# Laundry Order Management Specification

## 1. Scope

Single-store laundry workflow. No login/staff/store management.

System responsibilities:
- accept laundry groups + weight;
- decide which laundry may be merged;
- split laundry into machine-feasible batches;
- plan washer/dryer stages;
- prioritize pending work;
- calculate ETA and validate `pickup_at`;
- reschedule not-started work after relevant events;
- alert late/forgotten work;
- complete an order when the final customer notification is sent successfully.

Services:

```text
WASH
DRY
WASH_DRY
```

## 3. Status Model

### Order

The order status is derived from its batch stages:

```text
RECEIVED          // some CLASSIFY stage not completed
→ WAITING         // all CLASSIFY completed; machine stages remain
→ FOLDING_PACKING // only PACKING stages remain
→ READY           // every stage completed
→ COMPLETED       // final notification sent successfully
```

`COMPLETED` means the final notification was sent successfully. There is no separate customer-pickup completion step and no `NOTIFIED` order state.

### Batch

```text
WAITING                   // waiting for CLASSIFY, a machine, or PACKING
→ WASHING | DRYING
→ WAITING_FOR_UNLOAD
→ WAITING                 // next stage (machine stage or PACKING)
→ COMPLETED               // after PACKING completes
```

### Service flows (batch stages)

```text
WASH:     CLASSIFY → WASH → PACKING
DRY:      CLASSIFY → DRY → PACKING
WASH_DRY: CLASSIFY → WASH → DRY → PACKING
```

Machine stages go `PLANNED → IN_PROGRESS → MACHINE_FINISHED → COMPLETED`; `CLASSIFY` and `PACKING` go `PLANNED → COMPLETED` when staff confirm them.

## 4. Laundry Compatibility

Staff enters simple `item_type + weight`. The system maps `item_type` to a configured processing group.

### 4.1 Processing groups

```text
WHITE_NORMAL
LIGHT_NORMAL
DARK_NORMAL
BLACK_NORMAL
TOWEL_HEAVY
JEANS_HEAVY
SPORT
DELICATE
SPECIAL
```

`SPECIAL` means items requiring separate/custom handling.

### 4.2 Merge Matrix

Legend:

```text
Y = may merge when wash/dry requirements also match
N = do not merge
C = conditional; merge only when configured processing requirements match
```

| Group | WHITE_NORMAL | LIGHT_NORMAL | DARK_NORMAL | BLACK_NORMAL | TOWEL_HEAVY | JEANS_HEAVY | SPORT | DELICATE | SPECIAL |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| **WHITE_NORMAL** | Y | C | N | N | C | N | N | N | N |
| **LIGHT_NORMAL** | C | Y | N | N | C | N | N | N | N |
| **DARK_NORMAL** | N | N | Y | C | C | C | N | N | N |
| **BLACK_NORMAL** | N | N | C | Y | C | C | N | N | N |
| **TOWEL_HEAVY** | C | C | C | C | Y | C | N | N | N |
| **JEANS_HEAVY** | N | N | C | C | C | Y | N | N | N |
| **SPORT** | N | N | N | N | N | N | Y | N | N |
| **DELICATE** | N | N | N | N | N | N | N | Y | N |
| **SPECIAL** | N | N | N | N | N | N | N | N | C |

This matrix is a configurable business-rule baseline, not a universal textile-care rule.

Current implementation (`backend/src/services/planner.ts`): `C` is treated as `Y` because no per-item wash/dry/fabric/soil requirements are captured yet. `item_type` maps to a group through a fixed table, and unknown types become `SPECIAL`.

### 4.3 Conditional merge rule

For a matrix value `C`, merge only if all configured requirements match:

```text
wash_mode compatible
AND color-transfer rule allows merge
AND fabric/handling requirements compatible
AND soil requirements compatible
AND special handling compatible
AND, for DRY/WASH_DRY, dry_mode compatible
```

Precedence:

```text
care/special restriction
> fabric/handling rule
> soil rule
> color rule
```

```text
FUNCTION canMerge(a, b, service):

    relation = MERGE_MATRIX[a.group][b.group]

    IF relation == N:
        RETURN false

    IF special/care restriction conflicts:
        RETURN false

    IF wash requirements conflict:
        RETURN false

    IF fabric/handling conflicts:
        RETURN false

    IF soil requirements conflict:
        RETURN false

    IF service includes DRY
       AND dry requirements conflict:
        RETURN false

    RETURN true
```

Never infer a merge from weight alone.

## 5. Process

## P1 — Create Order

Input:

```text
customer
service_type
items[] = { item_type, quantity, weight_kg, note? }
pickup_at
special_note?
```

Flow:

```text
validate input
→ map item types to compatibility groups
→ generate batch plan
→ trial schedule
→ calculate ETA
→ validate pickup
```

Do not persist the final schedule until staff confirms a feasible plan.

---

## P2 — Build Compatibility Groups

1. Read all `ORDER_ITEMS`.
2. Apply the merge matrix + conditional rules.
3. Build groups containing only mutually compatible laundry.
4. Never merge incompatible groups.

Output:

```text
compatibilityGroups[]
```

---

## P3 — Generate Batches

Base algorithm: **Modified Best Fit Decreasing (BFD)**.

For each compatibility group:

```text
sort items by weight DESC

FOR each item:
    inspect existing batches
    reject incompatible placement
    reject placement with no feasible required machine

    newWeight = batch.weight + item.weight
    capacity = smallestFeasibleCapacity(newWeight, service)
    waste = capacity - newWeight

    choose feasible batch with minimum waste

    if none:
        create new batch
```

Machine feasibility:

```text
WASH:
exists washer.capacity >= batch.weight

DRY:
exists dryer.capacity >= batch.weight

WASH_DRY:
exists washer.capacity >= batch.weight
AND
exists dryer.capacity >= batch.weight
```

Approximate complexity:

```text
sort: O(n log n)
packing: O(n × b)
worst case: O(n²)
```

### Optional bounded local improvement

BFD is the fast base solution. To improve ETA, optionally generate a small number of neighboring plans:

```text
MOVE
SWAP
MERGE
SPLIT
```

Constraints remain mandatory.

Suggested bounds:

```text
MAX_ITERATIONS = 2..3
TOP_K = 10
ETA_TOLERANCE = 5 minutes
```

Do not exhaustively enumerate all weight partitions.

---

## P4 — Schedule Batches

### P4.1 Priority Queue

Scheduling priority is primarily **Least Slack Time**:

```text
slack =
pickup_at
- NOW
- remaining_processing_time
```

Lower slack = higher urgency.

Tie-breakers:

```text
1. higher manual priority
2. longer waiting time
3. earlier pickup_at
4. earlier created_at
```

Use a min-priority queue:

```text
peek O(1)
push O(log n)
pop  O(log n)
```

### P4.2 Select Machine

For the highest-priority ready stage, filter machines:

```text
machine.type matches stage
AND machine.capacity >= batch.weight
AND machine.status is operational
```

For each compatible machine:

```text
start =
MAX(stage.ready_at, machine.available_at)

finish =
start + machine.processing_minutes
```

Choose minimum `finish`.

Tie: prefer the smallest machine that fits.

Persist:

```text
machine_id
planned_start_at = start
planned_end_at = finish
```

For a small number of machines, scan compatible machines in `O(m)`; a machine heap is unnecessary.

For `WASH_DRY`:

```text
DRY.ready_at >= WASH.planned_end_at
```

If expected unloading time is modeled:

```text
DRY.ready_at
>= WASH.planned_end_at + expected_unload_time
```

---

## P5 — Evaluate Plan and ETA

Batch ETA is the `planned_end_at` of its `PACKING` stage, which already includes packing time.

Order ETA:

```text
estimated_at = MAX(all batch ETA)
```

Trial-schedule every retained candidate.

Reject plan if:

```text
compatibility violation
OR capacity violation
OR required stage has no feasible machine
OR new order ETA > requested pickup_at
OR any previously accepted order becomes late
```

Choose among valid plans lexicographically:

```text
1. earliest ETA
2. larger useful deadline buffer
3. fewer batches when ETA difference <= ETA_TOLERANCE
4. lower unused machine capacity as final tie-breaker
```

If no plan meets requested pickup, return earliest feasible pickup; do not commit the failed trial plan.

---

## P6 — Confirm Order

After staff accepts a feasible plan, persist:

```text
LAUNDRY_ORDER
ORDER_ITEMS
ORDER_BATCHES
BATCH_ITEMS
BATCH_STAGES
```

Persist planned machine/time assignments.

Set:

```text
order.status = RECEIVED
```

---

## P7 — Physical Classification

Each batch's `CLASSIFY` stage starts when the order is confirmed (`actual_started_at` is set). Staff physically verify the batch and confirm the stage:

```text
CLASSIFY.status = COMPLETED
batch.status = WAITING, current_stage = next stage
→ reschedule
```

When every batch's `CLASSIFY` stage is completed:

```text
order.classified_at = NOW
order.status = WAITING
```

Batch composition is not edited after confirmation.

---

## P8 — Start Machine Stage

Preconditions:

```text
batch = WAITING
stage = PLANNED (WASH or DRY)
machine available
machine type valid
capacity valid
```

On staff confirmation:

```text
actual_started_at = NOW
stage.status = IN_PROGRESS
machine.status = BUSY
batch.status = WASHING | DRYING
```

An `IN_PROGRESS` assignment is locked and non-preemptive.

---

## P9 — Machine Finishes / Unload

Machine cycle completion:

```text
actual_machine_finished_at = NOW
stage.status = MACHINE_FINISHED
batch.status = WAITING_FOR_UNLOAD
```

Machine remains unavailable while laundry is still inside.

After staff confirms unload:

```text
actual_ended_at = NOW
stage.status = COMPLETED
machine.status = AVAILABLE
```

Then:

```text
batch = WAITING
current_stage = next stage (DRY or PACKING)
```

A completion/unload event may trigger rescheduling.

---

## P10 — Folding and Packing

When every machine stage of every batch is completed:

```text
order.status = FOLDING_PACKING
```

Staff confirm each batch's `PACKING` stage:

```text
PACKING.status = COMPLETED
batch.status = COMPLETED
```

When every batch's `PACKING` stage is completed:

```text
packing_completed_at = NOW
ready_at = NOW
order.status = READY
```

`READY` cannot be reached while any batch has unfinished machine work, because `PACKING` only follows the last machine stage.

---

## P11 — Notify and Complete

Precondition:

```text
order.status = READY
```

Flow:

```text
generate notification draft
→ staff reviews/edits
→ staff presses Send
→ send notification
```

Success:

```text
notification.status = SENT
sent_at = NOW
completed_at = NOW
order.status = COMPLETED
```

Failure:

```text
notification.status = FAILED
order.status remains READY
```

There is no customer-pickup confirmation step.

---

## P12 — Event-Driven Rescheduling

Triggers:

```text
new order
pickup-time change
classification completed
packing completed
machine stage unloaded
machine failure
machine returns to service
stage finishes materially early/late
manual assignment change
```

Algorithm:

```text
lock IN_PROGRESS stages
→ collect not-started stages
→ recalculate Slack/priority
→ rebuild Priority Queue
→ reassign machines by earliest feasible finish
→ update planned_start_at/planned_end_at
→ recalculate batch ETA
→ recalculate order ETA
→ detect late risk
```

Rules:

```text
PLANNED     → machine/time may change
IN_PROGRESS → machine/time locked
```

Do not continuously reschedule without a relevant event.

---

## P13 — Change Pickup Time / Expedite

Do not update the real `pickup_at` first.

```text
staff enters new_pickup_at
→ clone current schedule
→ lock IN_PROGRESS
→ use new deadline in trial schedule
→ reprioritize pending stages
→ reschedule
→ recalculate affected ETAs
→ validate all accepted deadlines
```

If feasible:

```text
save APPOINTMENT_HISTORY
update pickup_at
commit trial schedule
```

If infeasible:

```text
discard trial changes
keep original pickup_at/schedule
show reason + affected orders
suggest earliest feasible pickup
```

---

## P14 — Alerts

### Late risk

Whenever ETA changes:

```text
IF estimated_at > pickup_at:
    create/update LATE_RISK
```

Optional warning:

```text
pickup_at - estimated_at <= warning_threshold
```

### Forgotten task

Monitor:

```text
WAITING too long
WAITING_FOR_UNLOAD too long
FOLDING_PACKING too long
READY because final notification has not succeeded
```

For unload:

```text
NOW - actual_machine_finished_at > unload_threshold
```

Snooze:

```text
snoozed_until = NOW + 5 minutes
```

After snooze:

```text
condition still true → show again
condition resolved   → resolve alert
```

Never create forgotten-task alerts for `COMPLETED`.

## 6. End-to-End Planning Pseudocode

```text
FUNCTION planOrder(order):

    groups =
        buildCompatibilityGroups(
            order.items,
            MERGE_MATRIX
        )

    initialPlan =
        modifiedBFD(
            groups,
            order.service_type,
            machines
        )

    candidates =
        boundedLocalSearch(
            initialPlan,
            optional = true
        )

    evaluated = []

    FOR candidate IN candidates:

        trial = copyCurrentSchedule()
        lockInProgressStages(trial)
        addCandidate(trial, candidate)

        queue =
            buildPriorityQueueBySlack(
                readyStages(trial)
            )

        schedulePendingStagesByEarliestFinish(
            trial,
            queue,
            machines
        )

        calculateETAs(trial)

        IF violatesHardConstraint(trial):
            CONTINUE

        evaluated.ADD(candidate, trial)

    IF evaluated is EMPTY:
        RETURN earliestFeasiblePickup()

    RETURN chooseBestPlan(
        evaluated,
        ETA_TOLERANCE
    )
```

## 7. Invariants / Agent Rules

Agents implementing or modifying the system must preserve these rules:

1. Never merge laundry when the compatibility matrix/rules reject the pair.
2. Never exceed machine capacity.
3. `WASH_DRY` batches must be feasible for both washer and dryer.
4. `BATCH_ITEMS` must preserve exact weight allocation.
5. Do not use order creation time as the primary scheduling rule.
6. Priority is primarily deadline Slack.
7. Select machines by earliest feasible finish, not availability alone.
8. Existing accepted deadlines must be protected when inserting/rescheduling work.
9. `IN_PROGRESS` stages are locked.
10. Machine cycle completion does not free the machine; unload confirmation does.
11. Multi-batch order ETA uses the last batch to finish, not sum of batch durations.
12. Trial changes must not mutate the committed schedule until confirmed.
13. `READY` requires all machine work + packing to be complete.
14. Successful final notification changes `READY → COMPLETED`.
15. Failed notification leaves the order `READY`.
16. There is no `NOTIFIED` order state and no customer-pickup completion step.
17. Alerts are not order statuses.
18. Rescheduling is event-driven.
